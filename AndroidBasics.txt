## Context — Android Notes ⭐⭐⭐⭐⭐

### 1. What is Context?

**Context represents the environment in which an Android component is running.**

It acts as a **bridge/reference between your application and the Android system**, allowing your code to access Android framework features.

```text
Your App
   ↓
Context
   ↓
Android Framework / OS
   ↓
System services, resources, activities, etc.
```

---

## 2. What can Context be used for?

Context provides access to many Android features:

```text
Context
   │
   ├── System Services
   │      ├── BatteryManager
   │      ├── PowerManager
   │      ├── NotificationManager
   │      └── ConnectivityManager
   │
   ├── Resources
   │      ├── Strings
   │      ├── Colors
   │      └── Drawables
   │
   ├── Start Activities
   │
   ├── Send/Register Broadcasts
   │
   ├── Application information
   │
   └── App files/preferences
```

Example:

```kotlin
val batteryManager =
    context.getSystemService(Context.BATTERY_SERVICE)
```

Here, `Context` helps your code obtain the Android `BatteryManager` system service.

---

# 3. Context is NOT a System Service

Don't confuse these:

```text
Context
   ↓
getSystemService()
   ↓
BatteryManager
```

`Context` provides a way to access Android services.

`BatteryManager` is the actual API that provides battery-related functionality.

---

# 4. Different types of Context

There is no separate "normal Context."

`Context` is the **base/abstract type**, and Android provides different Context implementations.

The two important ones for you are:

```text
                 Context
                    │
          ┌─────────┴─────────┐
          ↓                   ↓
 Activity Context      Application Context
```

---

# 5. Activity Context

An **Activity Context** is associated with a particular Activity.

For example:

```text
MainActivity
     ↓
Activity Context
```

Inside an Activity, you can commonly use:

```kotlin
this
```

as the Activity's Context.

Example:

```kotlin
val batteryManager =
    this.getSystemService(Context.BATTERY_SERVICE)
```

Activity Context is especially relevant when an operation needs to be associated with a particular Activity or its UI/window.

### Important point

An Activity has its own lifecycle:

```text
onCreate()
   ↓
onStart()
   ↓
onResume()
   ↓
...
   ↓
onDestroy()
```

Therefore, an Activity Context is tied to that Activity's lifecycle.

---

# 6. Application Context

**Application Context** represents the application-level environment.

You can obtain it using:

```kotlin
applicationContext
```

Conceptually:

```text
Application
     ↓
Application Context
     ↓
Whole application environment
```

It is **not tied to a particular Activity**.

Therefore, it is commonly appropriate for objects that need a Context for a long time and don't need an Activity/UI-specific Context.

Example:

```kotlin
val context = applicationContext
```

---

# 7. Activity Context vs Application Context

| Activity Context                                      | Application Context                  |
| ----------------------------------------------------- | ------------------------------------ |
| Associated with one Activity                          | Associated with the application      |
| Has Activity lifecycle                                | Lives with application process       |
| Can be appropriate for UI/Activity-related operations | Good for application-wide operations |
| Can be destroyed when Activity is destroyed           | Not tied to a particular Activity    |
| Avoid storing it in long-lived objects unnecessarily  | Safer for long-lived objects         |

### Simple mental model

```text
Activity Context
      ↓
"This particular Activity"

Application Context
      ↓
"This application"
```

---

# 8. Context and `getSystemService()`

One of the most common uses:

```kotlin
context.getSystemService(...)
```

For example:

```kotlin
val powerManager =
    context.getSystemService(Context.POWER_SERVICE)
```

```kotlin
val notificationManager =
    context.getSystemService(Context.NOTIFICATION_SERVICE)
```

```kotlin
val connectivityManager =
    context.getSystemService(Context.CONNECTIVITY_SERVICE)
```

So the general flow is:

```text
Context
   ↓
getSystemService()
   ↓
Android System Service
   ↓
Specific API
```

---

# 9. Context in Jetpack Compose

In Compose, you often see:

```kotlin
val context = LocalContext.current
```

`LocalContext.current` provides the current Android `Context` available to the Compose hierarchy.

For example:

```kotlin
@Composable
fun BatteryScreen() {

    val context = LocalContext.current

    val batteryManager =
        context.getSystemService(Context.BATTERY_SERVICE)
}
```

Flow:

```text
Compose
   ↓
LocalContext.current
   ↓
Context
   ↓
getSystemService()
   ↓
BatteryManager
```

This is exactly what you used in your battery project.

---

# 10. Why do we have different Contexts?

Because Android operations have **different scopes and lifecycles**.

For example:

```text
Need something related to a specific Activity?
        ↓
Activity Context
```

```text
Need something for long-lived/application-wide work?
        ↓
Application Context
```

Both are still `Context`.

---

# 11. Important warning — Context leaks

Suppose:

```text
Long-lived object
       ↓
holds MainActivity Context
       ↓
MainActivity gets destroyed
```

If the long-lived object continues holding that Activity reference, it can prevent the Activity from being garbage collected.

This can cause an **Activity memory leak**.

That's one reason developers need to choose the appropriate Context.

---

# 12. Context vs Activity

Remember:

```text
Activity is a Context
```

More precisely, `Activity` is a subclass of `ContextThemeWrapper`, which ultimately derives from `Context`.

Conceptually:

```text
Context
   ↑
ContextWrapper
   ↑
ContextThemeWrapper
   ↑
Activity
```

So an Activity can provide Context functionality.

---

# 13. Context vs `this`

Inside an Activity:

```kotlin
this
```

usually refers to the current Activity object.

Since an Activity is a Context:

```kotlin
this.getSystemService(...)
```

works.

You may also see:

```kotlin
this@MainActivity
```

when Kotlin needs you to explicitly refer to the Activity from a nested scope.

---

# 14. Context vs `applicationContext`

You might see:

```kotlin
context
```

and:

```kotlin
context.applicationContext
```

The first refers to whatever Context you currently have.

The second explicitly obtains the **Application Context**.

For example:

```kotlin
val activityContext: Context = this

val appContext: Context = this.applicationContext
```

---

# 15. Your battery project

Your project uses:

```kotlin
val context = LocalContext.current
```

Then:

```kotlin
val batteryManager =
    context.getSystemService(Context.BATTERY_SERVICE)
            as BatteryManager
```

The complete idea is:

```text
Compose UI
    ↓
LocalContext.current
    ↓
Context
    ↓
getSystemService()
    ↓
Android OS
    ↓
BatteryManager
    ↓
Battery information
```

So **Context is not the battery API**.

It is the Android environment/reference that lets your code interact with Android's framework.

---

## ⭐ Interview-ready definition

> **Context represents the environment associated with an Android application or component. It provides access to Android framework features such as system services, resources, application information, and component operations. Activity Context is associated with a particular Activity, while Application Context is associated with the application and is suitable for application-wide or long-lived operations.**

### 🧠 Remember these 5 points

```text

3. getSystemService() uses Context to obtain system services

4. Activity Context → specific Activity

5. Application Context → whole application
```

And your simplest mental model:

```text
             CONTEXT
                ↓
       "Where is my app/code
        operating in Android?"
                ↓
       ┌────────┴────────┐
       ↓                 ↓
 Activity Context   Application Context
       ↓                 ↓
  One Activity       Whole App
```

# Android Intent & Intent Filter — Complete Notes

## 1. What is an Intent?

An **Intent** is a message/request used by Android components to request an action from another component or from the Android system.

In simple words:

> **Intent = "I want something to happen."**

Example:

```kotlin
val intent = Intent(this, SecondActivity::class.java)
startActivity(intent)
```

Here the Intent tells Android:

> "I want to open `SecondActivity`."

### Common purposes of Intent

Intent can be used to:

1. Open another Activity
2. Send data between Activities
3. Start a Service
4. Send a Broadcast
5. Request an action from another application
6. Open a website
7. Open a dialer
8. Open maps
9. Share text/images/files
10. Handle deep links

---

# 2. What information can an Intent contain?

An Intent can contain information such as:

```text
Action
Data
Category
Extras
Component
Flags
```

The most important ones for understanding Intent Filters are:

```text
Action
Category
Data
```

---

# 3. Explicit Intent

An **Explicit Intent** specifies the exact component that should handle the request.

Example:

```kotlin
val intent = Intent(this, SecondActivity::class.java)
startActivity(intent)
```

Here you explicitly specify:

```text
SecondActivity
```

So Android doesn't need to search for another component.

### Flow

```text
Your App
   ↓
Explicit Intent
   ↓
SecondActivity
```

### Common uses

* Opening an Activity inside your own app
* Starting your own Service
* Communicating with a known component

---

# 4. Implicit Intent

An **Implicit Intent** does not specify the exact component.

Instead, it describes **what action you want to perform**.

Example:

```kotlin
val intent = Intent(
    Intent.ACTION_VIEW,
    Uri.parse("https://www.google.com")
)

startActivity(intent)
```

You are NOT saying:

```text
Open Chrome
```

You are saying:

```text
I want to VIEW this URL.
```

Android then determines which installed component can handle that request.

### Flow

```text
Your App
   ↓
Implicit Intent
   ↓
Android System
   ↓
Find matching component
   ↓
Open component
```

This is where **Intent Filters** become important.

---

# 5. What is an Intent Filter?

An **Intent Filter** is a declaration that tells Android what types of Intents a component can respond to.

It is normally declared in:

```text
AndroidManifest.xml
```

Example:

```xml
<intent-filter>

    <action android:name="android.intent.action.VIEW" />

    <category android:name="android.intent.category.DEFAULT" />

    <category android:name="android.intent.category.BROWSABLE" />

    <data android:scheme="https" />

</intent-filter>
```

In simple words:

> **Intent Filter = "I can handle these kinds of requests."**

---

# 6. Intent vs Intent Filter

This is the most important difference.

| Intent                        | Intent Filter                            |
| ----------------------------- | ---------------------------------------- |
| A message/request             | A matching declaration/rule              |
| Says what action is requested | Says what a component can handle         |
| Created by code or the system | Declared by a component                  |
| Can carry data                | Describes acceptable data                |
| Used to request an operation  | Used by Android during Intent resolution |

### Simple analogy

Think of a restaurant.

```text
Intent
   ↓
"I want pizza."
```

The restaurant's menu:

```text
Intent Filter
   ↓
"We serve pizza."
```

Android:

```text
"Which restaurant can satisfy this request?"
```

So:

```text
Intent = Request
Intent Filter = Capability/Matching declaration
Android = Matcher/Dispatcher
```

---

# 7. Where is Intent Filter declared?

Usually in:

```text
AndroidManifest.xml
```

Example:

```xml
<activity
    android:name=".MainActivity"
    android:exported="true">

    <intent-filter>

        <action android:name="android.intent.action.MAIN" />

        <category android:name="android.intent.category.LAUNCHER" />

    </intent-filter>

</activity>
```

Here the Intent Filter belongs to:

```text
MainActivity
```

So conceptually:

```text
MainActivity
     ↓
Intent Filter
     ↓
MAIN + LAUNCHER
```

---

# 8. What are the main parts of an Intent Filter?

An Intent Filter can specify:

```text
1. Action
2. Category
3. Data
```

---

## 8.1 Action

**Action** describes what operation the Intent is requesting.

Examples:

```text
ACTION_VIEW
ACTION_SEND
ACTION_EDIT
ACTION_MAIN
ACTION_DIAL
```

Example:

```xml
<action android:name="android.intent.action.VIEW" />
```

means:

> "This component can handle VIEW requests."

---

# 9. Category

A **Category** provides additional information about the Intent or the type of component that can handle it.

Example:

```xml
<category
    android:name="android.intent.category.LAUNCHER" />
```

This is used for an Activity that should appear as a launchable application.

Another important category:

```xml
<category
    android:name="android.intent.category.DEFAULT" />
```

This is important when an Activity is being considered as a target for implicit `startActivity()` requests.

---

# 10. Data

**Data** describes the type/content of data that the Intent is dealing with.

For a URL:

```text
https://www.google.com
```

the URI contains information such as:

```text
scheme = https
host = www.google.com
```

An Intent Filter can specify:

```xml
<data android:scheme="https" />
```

This means:

> "I can handle HTTPS URLs."

It can also be more specific:

```xml
<data
    android:scheme="https"
    android:host="www.google.com" />
```

This means the filter is intended for that particular host.

---

# 11. Who searches for the matching Intent Filter?

**The Android system performs Intent resolution.**

Your application normally does not manually search all installed apps when you call:

```kotlin
startActivity(intent)
```

The conceptual flow is:

```text
Your App
   ↓
Creates Intent
   ↓
startActivity(intent)
   ↓
Android System
   ↓
Intent Resolution
   ↓
Checks available components
   ↓
Checks their Intent Filters
   ↓
Finds matching component(s)
   ↓
Starts appropriate component
```

The Android framework's package/component information is used during this resolution process.

# 17. What exactly is Android matching?

Android considers the Intent's information against the Intent Filter's declared information.

The major concepts are:

```text
Intent                  Intent Filter

Action        ←→        Action
Category      ←→        Category
Data          ←→        Data
```

For our example:

```text
Intent:

ACTION = VIEW
URI = https://www.google.com
```

Possible filter:

```xml
<action android:name="android.intent.action.VIEW" />

<category android:name="android.intent.category.DEFAULT" />

<category android:name="android.intent.category.BROWSABLE" />

<data android:scheme="https" />
```

The filter indicates that the component can handle this kind of request.

---

# 18. What if multiple apps match?

Suppose:

```text
Chrome   → MATCH
Firefox  → MATCH
Brave    → MATCH
```

Android has multiple possible handlers.

Depending on the user's defaults and Android's resolution behavior, Android may:

* use the user's selected default app, or
* present a chooser asking which application to use.

For example:

```text
Open with

Chrome
Firefox
Brave
```

The user can select one.

# 19. What if only one app matches?

Suppose:

```text

Firefox  → NO
Brave    → NO
Maps     → NO
```

Then Android can launch the matching Activity.

The flow becomes:

```text
Your App
   ↓

   ↓

   ↓
Android System
   ↓
Intent Resolution
   ↓
Check available Intent Filters
   ↓
Chrome Activity matches
   ↓
Chrome Activity starts
   ↓
Chrome opens
https://www.google.com
```

# 20. What if nothing matches?

Suppose no installed Activity can handle the Intent.

Then Android cannot find a suitable component.

For example:

```text
Your App
   ↓
ACTION = SOME_UNKNOWN_ACTION
   ↓
Android
   ↓
No matching Intent Filter
   ↓
No Activity can handle request
```

Depending on how the Intent is used, this can result in an `ActivityNotFoundException` if your code tries to start an Activity and no suitable handler exists.

Suppose you have:


```text
       ↓
No Intent Filter needed for resolution
```

```text
       ↓
No specific component

       ↓
Intent Filters are important
```

Android uses that declaration during Intent resolution.

# 31. Final interview definition

If an interviewer asks:

### "What is an Intent?"

Say:

> **An Intent is a messaging object used by Android to request an action from another component or the Android system. It can be explicit, where a specific component is identified, or implicit, where Android determines a suitable component.**

### "What is an Intent Filter?"

Say:

> **An Intent Filter is a declaration in the application manifest that specifies the types of Intents a component can handle. Android uses these declarations during Intent resolution to find suitable components for implicit Intents.**

### "Who finds the matching Intent Filter?"

Say:

> **The Android system performs Intent resolution. It compares an implicit Intent with the Intent Filters declared by components of installed applications and determines suitable handlers.**

### "Give an example."

> **If my app sends an implicit Intent with `ACTION_VIEW` and the URI `https://www.google.com`, Android examines the Intent Filters of installed applications, finds components that can handle HTTPS VIEW requests, and then launches the appropriate handler or presents a chooser if multiple handlers are available.**

## Compose State — Notes ⭐⭐⭐⭐⭐

### 1. What is State?

**State** is a value that can change during the lifetime of the UI and whose change should be reflected in the UI.

Example:

```kotlin
var batteryLevel by remember {
    mutableStateOf(0)
}
```

Here:

```text
batteryLevel = State
0 → 50 → 75 → 100
```

Whenever the state changes, Compose can update the UI that depends on it.

---

## 2. `mutableStateOf()`

`mutableStateOf()` creates an **observable Compose state**.

```kotlin
val batteryState = mutableStateOf(0)
```

The actual value is accessed using:

```kotlin
batteryState.value
```

And changed using:

```kotlin
batteryState.value = 75
```

### Flow

```text
mutableStateOf(0)
       ↓
MutableState object
       ↓
stores value = 0
       ↓
value changes to 75
       ↓
Compose is notified
```

---

## 3. `remember`

`remember` keeps a value across **recompositions**.

```kotlin
val batteryState = remember {
    mutableStateOf(0)
}
```

Without `remember`, the state could be recreated when the composable executes again.

### Important

`remember`:

* survives **recomposition**
* does NOT mean permanent storage
* does NOT normally survive Activity recreation/process death

Think:

```text
remember = "Keep this value while this composable remains in the Composition."
```

---

## 4. `by` — Property Delegation

`by` is a **Kotlin feature** called **property delegation**.

Without `by`:

```kotlin
val batteryState = remember {
    mutableStateOf(0)
}

batteryState.value = 75

Text("${batteryState.value}%")
```

With `by`:

```kotlin
var batteryLevel by remember {
    mutableStateOf(0)
}

batteryLevel = 75

Text("$batteryLevel%")
```

`by` allows the `MutableState` object to handle the property's **get and set operations**.

### Easy definition

> **Delegation means giving the responsibility of an operation to another object.**

```text
batteryLevel
     ↓
delegates get/set
     ↓
MutableState object
```

---

# 5. Composition

**Composition** is the process where Compose initially executes your composable functions and builds the UI.

Example:

```kotlin
@Composable
fun BatteryScreen() {
    var batteryLevel by remember {
        mutableStateOf(0)
    }

    Text("Battery: $batteryLevel%")
}
```

Initially:

```text
BatteryScreen()
     ↓
Compose executes it
     ↓
batteryLevel = 0
     ↓
Text("Battery: 0%")
     ↓
Initial UI is created
```

This initial process is called **Composition**.

---

# 6. Recomposition

**Recomposition** happens when Compose detects that state used by a composable has changed.

Suppose:

```kotlin
batteryLevel = 75
```

Then:

```text
State changes
     ↓
Compose detects the change
     ↓
Affected composable scope is invalidated
     ↓
Recomposition is scheduled
     ↓
Relevant composable code executes again
     ↓
UI is updated
```

So:

```text
Composition
= Initial creation of UI

Recomposition
= Re-execution of affected composable code
  when observed state changes
```

---

# 7. Complete Battery Example

```kotlin
@Composable
fun BatteryScreen() {

    var batteryLevel by remember {
        mutableStateOf(0)
    }

    Text(
        text = "Battery: $batteryLevel%"
    )
}
```

Suppose initially:

```text
batteryLevel = 0
```

UI:

```text
Battery: 0%
```

Then your battery logic gets:

```text
75%
```

and does:

```kotlin
batteryLevel = 75
```

Now:

```text
batteryLevel
      ↓
value changed
      ↓
MutableState notifies Compose
      ↓
Compose knows the UI read this state
      ↓
Recomposition
      ↓
Text("Battery: 75%")
      ↓
UI displays 75%
```

---

# 8. `rememberSaveable`

`rememberSaveable` is similar to `remember`, but it can restore supported state using Android's saved-state mechanism, such as after configuration changes.

```kotlin
var count by rememberSaveable {
    mutableStateOf(0)
}
```

### Difference

| Feature                            | `remember`  | `rememberSaveable`     |
| ---------------------------------- | ----------- | ---------------------- |
| Survives recomposition             | ✅           | ✅                      |
| Restores after Activity recreation | ❌ generally | ✅ for supported values |
| Permanent storage                  | ❌           | ❌                      |
| Database                           | ❌           | ❌                      |

For your battery app, you normally don't need to save the battery percentage because you can query the current battery information again.

---

# 9. `State` vs UI

State and UI are different.

```text
STATE
batteryLevel = 75
       ↓
UI represents the state
       ↓
"Battery: 75%"
```

So:

> **State = data**

> **UI = representation of that data**

# 10. The Four Important Concepts

Remember these four:

```text
mutableStateOf()
        ↓
Creates observable state

remember
        ↓
Keeps state across recomposition

by
        ↓
Kotlin property delegation
        ↓
Allows direct access instead of .value

recomposition
        ↓
Compose re-executes affected
composable code when observed
state changes
```

### Interview-ready answer

> **Compose State is data that can change and affect the UI. `mutableStateOf()` creates observable state, `remember` retains that state across recompositions, and `by` uses Kotlin property delegation to simplify access to the state's value. When an observed state changes, Compose detects the change and performs recomposition of the affected composable scopes, allowing the UI to display the new state.**

**Launch modes** control **how Android creates or reuses an `Activity` when you start it**.

Don't confuse this with the **Launcher** we just discussed.

* **Launcher** → starts your app from the phone's home/app drawer.
* **Launch mode** → controls what Android does with an Activity when you call `startActivity()`.

### Simple example

Suppose you have:

```text
MainActivity
SecondActivity
```

From `MainActivity`:

```kotlin
startActivity(Intent(this, SecondActivity::class.java))
```

Normally Android creates a **new instance** of `SecondActivity`.

But launch modes can change this behavior.

There are 4 important launch modes:

| Launch mode      | Simple meaning                                                        |
| ---------------- | --------------------------------------------------------------------- |
| `standard`       | Create a new Activity instance every time                             |
| `singleTop`      | Reuse the existing Activity if it is already **on top**               |
| `singleTask`     | Reuse an existing Activity in the task and remove Activities above it |
| `singleInstance` | Activity gets its own separate task                                   |

---

### 1. `standard`

Default behavior.

```text
MainActivity
    ↓
SecondActivity
    ↓
SecondActivity
    ↓
SecondActivity
```

Every time you call:

```kotlin
startActivity(Intent(this, SecondActivity::class.java))
```

Android creates another `SecondActivity`.

So you can have:

```text
SecondActivity #1
SecondActivity #2
SecondActivity #3
```

---

### 2. `singleTop`

Suppose:

```text
MainActivity
    ↓
SecondActivity
```

Now you start `SecondActivity` again.

Because `SecondActivity` is already **at the top**, Android reuses it.

```text
MainActivity
    ↓
SecondActivity
```

It does **not** create another one.

But if:

```text
MainActivity
    ↓
SecondActivity
    ↓
ThirdActivity
```

and you start `SecondActivity` again, `SecondActivity` isn't on top.

So Android can create another one:

```text
MainActivity
    ↓
SecondActivity #1
    ↓
ThirdActivity
    ↓
SecondActivity #2
```

---

### 3. `singleTask`

This is different.

Suppose:

```text
MainActivity
    ↓
SecondActivity
    ↓
ThirdActivity
```

If `SecondActivity` is `singleTask` and you start it again:

```text
MainActivity
    ↓
SecondActivity
```

`ThirdActivity` is removed.

Android brings the existing `SecondActivity` to the front instead of creating another instance.

---

### 4. `singleInstance`

This puts the Activity in its **own task**.

It's a more specialized mode and is much less common in normal application development.

---

### Where do we specify launch mode?

In `AndroidManifest.xml`:

```xml
<activity
    android:name=".SecondActivity"
    android:launchMode="singleTop" />
```

Or you can control some launch behavior through flags on the `Intent`.

### Most important distinction

Don't mix these three:

```text
LAUNCHER
   ↓
Can this Activity be launched from the phone's launcher?

launchMode
   ↓
How should Android create/reuse this Activity?

Intent
   ↓
What action/request do I want Android to perform?
```

So if an interviewer asks **"What is launch mode?"**, a good answer is:

> **“Launch mode defines how Android creates or reuses an Activity instance when that Activity is launched. The main modes are standard, singleTop, singleTask, and singleInstance.”**

## 1. Activity — "I need a screen"

You already know this one.

An `Activity` represents a **screen/UI entry point**.

For example:

```text
MainActivity
     ↓
Login screen
```

When the user opens your app:

```text
Launcher
   ↓
MainActivity
   ↓
UI appears
```

So:

> **Activity = component used to provide a user interface/screen.**

# 2. Service — "I need to do something without a screen"

A **Service** is an Android component designed for work that doesn't require a user interface.

Imagine:

```text
You open Spotify
      ↓
Start playing music
      ↓
You leave Spotify
      ↓
Open WhatsApp
      ↓
Music continues
```

The music doesn't need Spotify's screen to remain visible.

That's the kind of situation where a **Service** can be involved.

Conceptually:

```text
Activity
   ↓
starts Service
   ↓
Service performs work
   ↓
Activity can disappear
   ↓
Work can continue according to Android's service rules
```

### Another example

A navigation app could have:

```text

       ↓
User starts navigation
       ↓
Location-related work
       ↓
User locks phone
       ↓
Navigation-related work continues
```

Again, the important idea is:

> **Service = a component for work that may need to continue without an Activity's UI being visible.**

### Important beginner point

Don't think:

> "Service = anything that runs in the background forever."

That's **not correct**.

Modern Android puts restrictions on background execution, and different types of services exist, including **foreground services** for work that needs to remain noticeable to the user.

# 3. BroadcastReceiver — "Something happened; react to it"

Now this one is different.

A **BroadcastReceiver** waits for a **broadcast event** and reacts when that event occurs.

Imagine your phone's Android system saying:

```text

```

or:

```text
"Phone has finished booting!"
```

or:

```text
"Power connected!"
```

A BroadcastReceiver can listen for appropriate broadcasts and execute code when they occur.

Think of it like a **doorbell**.

```text
Event happens
     ↓
Broadcast
     ↓
BroadcastReceiver hears it
     ↓
Your code runs
```

# Android Service, Broadcast & BroadcastReceiver

## 1. Service

A **Service** is an Android application component used to perform work **without a user interface (UI)**.

A Service can continue working even when the user is not directly interacting with a screen.

### Example

In our project:

```text
BatteryReceiver
      ↓
startService()
      ↓
BatteryService
      ↓
Process battery data
      ↓
stopSelf()
```

The Service doesn't display anything on the screen. It performs its work separately from the UI.

### Important point

A Service **does not automatically run on a separate thread**.

If heavy work is performed inside a Service, you may need:

* Coroutines
* Threads
* Other background mechanisms

---

# 2. Types of Service

There are two important ways a Service can be used.

### Started Service

Started using:

```kotlin
startService(intent)
```

Android calls:

```kotlin
onStartCommand()
```

Example:

```text
startService()
     ↓
onCreate()
     ↓
onStartCommand()
     ↓
Work
     ↓
stopSelf()
     ↓
onDestroy()
```

This is the type used in our Battery project.

### Bound Service

Used when another component wants to **connect and communicate with the Service**.

```kotlin
bindService(...)
```

It uses:

```kotlin
onBind()
```

For our project, we are **not using a Bound Service**.

---

# 3. Service Lifecycle

For our Started Service:

```text
startService()
      ↓
onCreate()
      ↓
onStartCommand()
      ↓
Perform work
      ↓
stopSelf()
      ↓
onDestroy()
```

### `onCreate()`

Called when the Service is created.

Used for initialization.

```kotlin
override fun onCreate() {
    super.onCreate()
}
```

### `onStartCommand()`

Called when the Service receives a start request.

This is where the main Service work is normally performed.

```kotlin
override fun onStartCommand(
    intent: Intent?,
    flags: Int,
    startId: Int
): Int {
    return START_NOT_STICKY
}
```

### `onDestroy()`

Called when the Service is being destroyed.

Used for cleanup.

### `onBind()`

Required when extending `Service`, but for our Started Service we return:

```kotlin
override fun onBind(intent: Intent?): IBinder? {
    return null
}
```

We are not using Bound Service functionality.

---

# 4. Broadcast

A **Broadcast** is a message/event sent by Android or an application to notify interested components that **something happened**.

Think of it as:

> **"Something happened. Anyone interested can receive this message."**

Examples of Android broadcasts:

```text
Battery changed
Device boot completed
Airplane mode changed
Charging state changed
Screen turned on/off
```

In our project, we use:

```kotlin
Intent.ACTION_BATTERY_CHANGED
```

This is a system broadcast related to battery state.

---

# 5. BroadcastReceiver

A **BroadcastReceiver** is an Android component that **receives and responds to broadcasts**.

It has:

```kotlin
override fun onReceive(
    context: Context,
    intent: Intent
)
```

The `onReceive()` method runs when the receiver receives a matching broadcast.

### Simple flow

```text
Android System
      ↓
Broadcast
"A battery change happened"
      ↓
BroadcastReceiver
      ↓
onReceive()
      ↓
Process the information
```

---

# 6. IntentFilter

A **BroadcastReceiver** needs to know which broadcasts it is interested in.

We use an `IntentFilter`.

In our project:

```kotlin
val filter = IntentFilter(
    Intent.ACTION_BATTERY_CHANGED
)
```

This means:

> "I am interested in battery-change broadcasts."

Then:

```kotlin
registerReceiver(
    batteryReceiver,
    filter
)
```

registers the receiver.

---

# 7. Battery Broadcast in Our Project

The Android system sends:

```text
ACTION_BATTERY_CHANGED
```

The broadcast `Intent` contains battery-related information as **extras**.

For example:

```text
EXTRA_LEVEL
EXTRA_SCALE
EXTRA_STATUS
EXTRA_VOLTAGE
EXTRA_TEMPERATURE
EXTRA_HEALTH
EXTRA_TECHNOLOGY
```

Our receiver extracts them:

```kotlin
val level = intent.getIntExtra(
```

So the `Intent` is carrying the data.

# 8. BroadcastReceiver → Activity

Our receiver sends the extracted information to `BatteryActivity` through a callback.

```text
Android
   ↓
Battery Broadcast
   ↓
BatteryReceiver
   ↓
onBatteryChanged(...)
   ↓
BatteryActivity
   ↓
Compose State
   ↓
UI updates
```

For example:

```kotlin
onBatteryChanged(
    batteryPercentage,
    chargingStatus,
    voltage,
    temperature,
    health,
    technology
)
```

The Activity then updates:

```kotlin
batteryLevel.value = level
```

Compose detects the state change and recomposes the UI.

# 9. BroadcastReceiver → Service

Our receiver also sends the battery information to the Service.

First we create an explicit Intent:

```kotlin
val serviceIntent = Intent(
    context,
    BatteryService::class.java
)
```

Then we put the battery data into it:

```kotlin
serviceIntent.putExtra(
    "batteryLevel",
    batteryPercentage
)

serviceIntent.putExtra(
    "chargingStatus",
    chargingStatus
)
```

Then:

```kotlin
context.startService(serviceIntent)
```

The Service receives the Intent in:

```kotlin
onStartCommand()
```

and extracts the data:

```kotlin
val batteryLevel =
    intent?.getIntExtra(
        "batteryLevel",
        0
    ) ?: 0
```
