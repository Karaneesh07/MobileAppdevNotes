# Android Intent & Intent Filter — Complete Notes

## 1. What is an Intent?

An **Intent** is a message/request used by Android components to request an action from another component or from the Android system.

In simple words:

> **Intent = "I want something to happen."**

Example:

```kotlin
val intent = Intent(this, SecondActivity::class.java)
startActivity(intent)
```

Here the Intent tells Android:

> "I want to open `SecondActivity`."

### Common purposes of Intent

Intent can be used to:

1. Open another Activity
2. Send data between Activities
3. Start a Service
4. Send a Broadcast
5. Request an action from another application
6. Open a website
7. Open a dialer
8. Open maps
9. Share text/images/files
10. Handle deep links

---

# 2. What information can an Intent contain?

An Intent can contain information such as:

```text
Action
Data
Category
Extras
Component
Flags
```

The most important ones for understanding Intent Filters are:

```text
Action
Category
Data
```

---

# 3. Explicit Intent

An **Explicit Intent** specifies the exact component that should handle the request.

Example:

```kotlin
val intent = Intent(this, SecondActivity::class.java)
startActivity(intent)
```

Here you explicitly specify:

```text
SecondActivity
```

So Android doesn't need to search for another component.

### Flow

```text
Your App
   ↓
Explicit Intent
   ↓
SecondActivity
```

### Common uses

* Opening an Activity inside your own app
* Starting your own Service
* Communicating with a known component

---

# 4. Implicit Intent

An **Implicit Intent** does not specify the exact component.

Instead, it describes **what action you want to perform**.

Example:

```kotlin
val intent = Intent(
    Intent.ACTION_VIEW,
    Uri.parse("https://www.google.com")
)

startActivity(intent)
```

You are NOT saying:

```text
Open Chrome
```

You are saying:

```text
I want to VIEW this URL.
```

Android then determines which installed component can handle that request.

### Flow

```text
Your App
   ↓
Implicit Intent
   ↓
Android System
   ↓
Find matching component
   ↓
Open component
```

This is where **Intent Filters** become important.

---

# 5. What is an Intent Filter?

An **Intent Filter** is a declaration that tells Android what types of Intents a component can respond to.

It is normally declared in:

```text
AndroidManifest.xml
```

Example:

```xml
<intent-filter>

    <action android:name="android.intent.action.VIEW" />

    <category android:name="android.intent.category.DEFAULT" />

    <category android:name="android.intent.category.BROWSABLE" />

    <data android:scheme="https" />

</intent-filter>
```

In simple words:

> **Intent Filter = "I can handle these kinds of requests."**

---

# 6. Intent vs Intent Filter

This is the most important difference.

| Intent                        | Intent Filter                            |
| ----------------------------- | ---------------------------------------- |
| A message/request             | A matching declaration/rule              |
| Says what action is requested | Says what a component can handle         |
| Created by code or the system | Declared by a component                  |
| Can carry data                | Describes acceptable data                |
| Used to request an operation  | Used by Android during Intent resolution |

### Simple analogy

Think of a restaurant.

```text
Intent
   ↓
"I want pizza."
```

The restaurant's menu:

```text
Intent Filter
   ↓
"We serve pizza."
```

Android:

```text
"Which restaurant can satisfy this request?"
```

So:

```text
Intent = Request
Intent Filter = Capability/Matching declaration
Android = Matcher/Dispatcher
```

---

# 8. What are the main parts of an Intent Filter?

An Intent Filter can specify:

```text
1. Action
2. Category
3. Data
```

## 8.1 Action

**Action** describes what operation the Intent is requesting.

Examples:

```text
ACTION_VIEW
ACTION_SEND
ACTION_EDIT
ACTION_MAIN
ACTION_DIAL
```

Example:

```xml
<action android:name="android.intent.action.VIEW" />
```

means:

> "This component can handle VIEW requests."

---

# 9. Category

A **Category** provides additional information about the Intent or the type of component that can handle it.

Example:

```xml
<category
    android:name="android.intent.category.LAUNCHER" />
```

This is used for an Activity that should appear as a launchable application.

Another important category:

```xml
<category
    android:name="android.intent.category.DEFAULT" />
```

This is important when an Activity is being considered as a target for implicit `startActivity()` requests.

---

# 10. Data

**Data** describes the type/content of data that the Intent is dealing with.

For a URL:

```text
https://www.google.com
```

the URI contains information such as:

```text
scheme = https
host = www.google.com
```

An Intent Filter can specify:

```xml
<data android:scheme="https" />
```

This means:

> "I can handle HTTPS URLs."

It can also be more specific:

```xml
<data
    android:scheme="https"
    android:host="www.google.com" />
```

This means the filter is intended for that particular host.

# 11. Who searches for the matching Intent Filter?

**The Android system performs Intent resolution.**

Your application normally does not manually search all installed apps when you call:

```kotlin
startActivity(intent)
```

The conceptual flow is:

```text
Your App
   ↓
Creates Intent
   ↓
startActivity(intent)
   ↓
Android System
   ↓
Intent Resolution
   ↓
Checks available components
   ↓
Checks their Intent Filters
   ↓
Finds matching component(s)
   ↓
Starts appropriate component
```

The Android framework's package/component information is used during this resolution process.

## Compose State — Notes ⭐⭐⭐⭐⭐

### 1. What is State?

**State** is a value that can change during the lifetime of the UI and whose change should be reflected in the UI.

Example:

```kotlin
var batteryLevel by remember {
    mutableStateOf(0)
}
```

Here:

```text
batteryLevel = State
0 → 50 → 75 → 100
```

Whenever the state changes, Compose can update the UI that depends on it.

---

## 2. `mutableStateOf()`

`mutableStateOf()` creates an **observable Compose state**.

```kotlin
val batteryState = mutableStateOf(0)
```

The actual value is accessed using:

```kotlin
batteryState.value
```

And changed using:

```kotlin
batteryState.value = 75
```

### Flow

```text
mutableStateOf(0)
       ↓
MutableState object
       ↓
stores value = 0
       ↓
value changes to 75
       ↓
Compose is notified
```

---

## 3. `remember`

`remember` keeps a value across **recompositions**.

```kotlin
val batteryState = remember {
    mutableStateOf(0)
}
```

Without `remember`, the state could be recreated when the composable executes again.

### Important

`remember`:

* survives **recomposition**
* does NOT mean permanent storage
* does NOT normally survive Activity recreation/process death

Think:

```text
remember = "Keep this value while this composable remains in the Composition."
```

---

## 4. `by` — Property Delegation

`by` is a **Kotlin feature** called **property delegation**.

Without `by`:

```kotlin
val batteryState = remember {
    mutableStateOf(0)
}

batteryState.value = 75

Text("${batteryState.value}%")
```

With `by`:

```kotlin
var batteryLevel by remember {
    mutableStateOf(0)
}

batteryLevel = 75

Text("$batteryLevel%")
```

`by` allows the `MutableState` object to handle the property's **get and set operations**.

### Easy definition

> **Delegation means giving the responsibility of an operation to another object.**

```text
batteryLevel
     ↓
delegates get/set
     ↓
MutableState object
```

---

# 5. Composition

**Composition** is the process where Compose initially executes your composable functions and builds the UI.

Example:

```kotlin
@Composable
fun BatteryScreen() {
    var batteryLevel by remember {
        mutableStateOf(0)
    }

    Text("Battery: $batteryLevel%")
}
```

Initially:

```text
BatteryScreen()
     ↓
Compose executes it
     ↓
batteryLevel = 0
     ↓
Text("Battery: 0%")
     ↓
Initial UI is created
```

This initial process is called **Composition**.

---

# 6. Recomposition

**Recomposition** happens when Compose detects that state used by a composable has changed.

Suppose:

```kotlin
batteryLevel = 75
```

Then:

```text
State changes
     ↓
Compose detects the change
     ↓
Affected composable scope is invalidated
     ↓
Recomposition is scheduled
     ↓
Relevant composable code executes again
     ↓
UI is updated
```

So:

```text
Composition
= Initial creation of UI

Recomposition
= Re-execution of affected composable code
  when observed state changes
```

---

```kotlin
    }
```

UI:


# 8. `rememberSaveable`

`rememberSaveable` is similar to `remember`, but it can restore supported state using Android's saved-state mechanism, such as after configuration changes.

```kotlin
var count by rememberSaveable {
    mutableStateOf(0)
}
```

### Difference

| Feature                            | `remember`  | `rememberSaveable`     |
| ---------------------------------- | ----------- | ---------------------- |
| Survives recomposition             | ✅           | ✅                      |
| Restores after Activity recreation | ❌ generally | ✅ for supported values |
| Permanent storage                  | ❌           | ❌                      |
| Database                           | ❌           | ❌                      |

For your battery app, you normally don't need to save the battery percentage because you can query the current battery information again.

# 9. `State` vs UI

State and UI are different.

```text
STATE
batteryLevel = 75
       ↓
UI represents the state
       ↓
"Battery: 75%"
```

So:

> **State = data**

> **UI = representation of that data**

# 10. The Four Important Concepts

Remember these four:

```text
mutableStateOf()
        ↓
Creates observable state

remember
        ↓
Keeps state across recomposition

by
        ↓
Kotlin property delegation
        ↓
Allows direct access instead of .value

recomposition
        ↓
Compose re-executes affected
composable code when observed
state changes
```

### Interview-ready answer

> **Compose State is data that can change and affect the UI. `mutableStateOf()` creates observable state, `remember` retains that state across recompositions, and `by` uses Kotlin property delegation to simplify access to the state's value. When an observed state changes, Compose detects the change and performs recomposition of the affected composable scopes, allowing the UI to display the new state.**

**Launch modes** control **how Android creates or reuses an `Activity` when you start it**.

Don't confuse this with the **Launcher** we just discussed.

* **Launcher** → starts your app from the phone's home/app drawer.
* **Launch mode** → controls what Android does with an Activity when you call `startActivity()`.

### Simple example

Suppose you have:

```text
MainActivity
SecondActivity
```

From `MainActivity`:

```kotlin
startActivity(Intent(this, SecondActivity::class.java))
```

Normally Android creates a **new instance** of `SecondActivity`.

But launch modes can change this behavior.

There are 4 important launch modes:

| Launch mode      | Simple meaning                                                        |
| ---------------- | --------------------------------------------------------------------- |
| `standard`       | Create a new Activity instance every time                             |
| `singleTop`      | Reuse the existing Activity if it is already **on top**               |
| `singleTask`     | Reuse an existing Activity in the task and remove Activities above it |
| `singleInstance` | Activity gets its own separate task                                   |

---

### 1. `standard`

Default behavior.

```text
MainActivity
    ↓
SecondActivity
    ↓
SecondActivity
    ↓
SecondActivity
```

Every time you call:

```kotlin
startActivity(Intent(this, SecondActivity::class.java))
```

Android creates another `SecondActivity`.

So you can have:

```text
SecondActivity #1
SecondActivity #2
SecondActivity #3
```

---

### 2. `singleTop`

Suppose:

```text
MainActivity
    ↓
SecondActivity
```

Now you start `SecondActivity` again.

Because `SecondActivity` is already **at the top**, Android reuses it.

```text
MainActivity
    ↓
SecondActivity
```

It does **not** create another one.

But if:

```text
MainActivity
    ↓
SecondActivity
    ↓
ThirdActivity
```

and you start `SecondActivity` again, `SecondActivity` isn't on top.

So Android can create another one:

```text
MainActivity
    ↓
SecondActivity #1
    ↓
ThirdActivity
    ↓
SecondActivity #2
```

---

### 3. `singleTask`

This is different.

Suppose:

```text
MainActivity
    ↓
SecondActivity
    ↓
ThirdActivity
```

If `SecondActivity` is `singleTask` and you start it again:

```text
MainActivity
    ↓
SecondActivity
```

`ThirdActivity` is removed.

Android brings the existing `SecondActivity` to the front instead of creating another instance.

---

### 4. `singleInstance`

This puts the Activity in its **own task**.

It's a more specialized mode and is much less common in normal application development.

---

### Where do we specify launch mode?

In `AndroidManifest.xml`:

```xml
<activity
    android:name=".SecondActivity"
    android:launchMode="singleTop" />
```

Or you can control some launch behavior through flags on the `Intent`.

### Most important distinction

Don't mix these three:

```text
LAUNCHER
   ↓
Can this Activity be launched from the phone's launcher?

launchMode
   ↓
How should Android create/reuse this Activity?

Intent
   ↓
What action/request do I want Android to perform?
```

So if an interviewer asks **"What is launch mode?"**, a good answer is:

> **“Launch mode defines how Android creates or reuses an Activity instance when that Activity is launched. The main modes are standard, singleTop, singleTask, and singleInstance.”**
